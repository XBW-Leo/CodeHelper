# 代码审查

## 何时使用

- 用户要求审查当前改动、PR 或指定文件
- 提交前想自查质量
- 排查可疑的回归或安全隐患

## 流程

1. **确定范围**：默认审查 `git diff` 与 `git diff --cached`；用户指定时审查对应文件、目录或 commit 范围。
2. **通读上下文**：阅读被改动代码及其调用方、数据流；不要只看 diff 片段。必要时用只读命令（`rg`、`ls`、`git log`）验证。
3. **检查清单**：
   - 逻辑正确性与边界条件
   - 错误处理与异常路径
   - 安全隐患（注入、密钥、权限）
   - 性能与复杂度（不必要的重计算、N+1、内存）
   - 可维护性（命名、重复、耦合、注释是否准确）
   - 测试覆盖（关键路径是否有测试）
4. **输出结构**：
   - 概览：改动意图与影响面
   - 优点
   - 问题：按严重程度排序
   - 测试：覆盖情况与缺失
   - 建议：按优先级排序的具体修改建议

## 规则

- 只审查，不修改代码（除非用户明确要求修复）。
- 每个问题都要给出位置和理由，不要只给"建议优化"这类空话。
- 若没有发现问题，明确说明。
